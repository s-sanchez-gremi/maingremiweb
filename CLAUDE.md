# Apex — build guide for Claude Code

This file orients Claude Code (or any engineer) starting the Apex project. It summarizes the plan and mockups already agreed with the client; treat it as the source of truth until superseded by code or a written decision.

## Read first: team sync notices
**At the start of every session, read `docs/team-sync.md`** and do any open item addressed to the person you are working for (Joan Marc / Sam). It lists what the other side changed that you must act on (migrations, moved tables, new rules). Add a notice there whenever you change something the other person's side must act on.

## Git workflow (team decision: 2 people, Claude merges)
- **Never commit or push to `main` directly.** Every change, however small, goes on its own branch created from the latest `main` (`git fetch origin main && git checkout -b <branch> origin/main`).
- **One branch per task/person.** Two people work in parallel, so never commit on someone else's branch unless asked; never rewrite history (rebase, amend, force-push) on a branch already pushed.
- **Merging is done by Claude** through a pull request to `main`: only when CI is green and there is no conflict. If `main` moved, merge `main` into the branch first (merge commit, not rebase), re-run checks, then merge the PR. If both branches changed the same logic, ask before choosing.
- After a branch is merged, follow-up work starts on a fresh branch from `main`; a merged branch is never reused.

## What Apex is

Three parts, one shared backend:

1. **Public website** — a content site (blog posts + themed landing pages) visible to everyone.
2. **Internal backend** — staff-only. Doubles as CRM, ERP, project manager and client manager.
3. **Client portal** — clients log in to see their own projects, documents and invoices (later phase).

**This guide covers the backbone: the public website + the backend content, lead-capture and form-builder pieces underneath it.** The full CRM/ERP/project-manager modules and the client portal are separate, later phases — don't build them yet (only the minimal Clients/Projects records that forms can attach to exist; see phase 6).

## Core priorities (apply to every decision below)

1. **Simplicity and robustness over new, interactive or complex features.** When two approaches solve the same problem, pick the plainer, more battle-tested one, even if it's less flashy.
2. **One database, one API, no separate systems.** Content, leads and form submissions all live in the same Postgres database and are served through the same API. Never wire the public site to a separate CMS/lead tool.
3. **No freeform canvas editors anywhere in the backend.** Pages, posts and forms are all built from a fixed, ordered list of typed sections/fields — add, reorder (up/down), remove. Never pixel/absolute positioning, never per-item custom CSS. *Client decision (phase 13):* pages also get a visual, Elementor-style builder with drag and drop, but it only moves sections and blocks within that same ordered list and columns, and styles are a fixed set of brand choices (see "Visual page builder").
4. **Public pages are pre-rendered** (SSR/SSG) for speed, SEO, and so the site survives a backend outage.
5. **Consistent look by construction.** Every section/field renders with the site's fixed design tokens (below). Editors fill in content; they never choose fonts, colors or layout.

## Recommended stack

- **Next.js** for the public site, the CMS admin, the CRM and the forms: one repository, separate apps (`apps/web`, `apps/admin`, `apps/crm`, `apps/forms` in progress) sharing packages and one database.
- **PostgreSQL** (EU region) as the single database.
- **A custom, minimal CMS** built in the same Next.js app (decision by client, replaces the earlier Payload suggestion): Drizzle ORM + Zod on Postgres. See "Custom CMS design" below — keep it as small and generic as described there.
- **S3-compatible object storage** for images/files.
- **A transactional email service** for notifications.

Alternatives (Astro + headless CMS, WordPress) were considered and rejected because they split content and CRM/lead data into separate systems, violating priority 2.

## Custom CMS design


**Principle: a few generic parts, reused everywhere. New content or fields = data/config, not new code.**

#### Tables (8 total)
`users` (email, password_hash, role admin|editor) · `sessions` · `entries` (type `post`|`page`, theme, category_id, author_id, tags text[], cover media_id, publish date) · `entry_translations` (entry_id, locale, title, slug, `sections` jsonb, seo jsonb, status, publish_at) · `categories` (+ names jsonb per locale) · `media` (key, alt jsonb per locale, credit) · `forms` (fields jsonb, destination, notifications, consent jsonb per locale) · `settings` (single row, jsonb: nav, footer, SEO, contact, cookie text).
Lead tables (`contacts`, `leads`, `submissions`, `newsletter_optins`) are separate and belong to the lead pipeline.
Posts and landing pages share **one** `entries` table; the only difference is `type`.

#### Five generic building blocks
1. **Section registry** — lives in the shared package `packages/sections` (`@apex/sections/registry`, `/blocks`: pure data + zod, no React, no database, so the website and the CMS admin share ONE definition of a page); each type has `{ name, label, fields }` and its renderer is in `apps/web/sections/render.tsx`. `fields` is a tiny declarative list (`text`, `textarea`, `image`, `link`, `select`, `list`). Zod validation and the **admin form are generated from `fields`**, so adding a section type = **one file, no admin code**. Sections: header, text, image, embed, form, CTA, tile row, card grid.
2. **`<ListEditor>`** — one component: add from a picker, ↑ ↓ ✕. Used for page sections **and** form fields **and** nav/footer links. Not built three times.
3. **Generic entity screens** — a list screen and an edit screen driven by config, reused for entries, categories, media, forms, users. No hand-built screen per content type.
4. **`translations` pattern** — every localized thing is `jsonb {ca,es,en}` or a translation row; one helper resolves locale with fallback to `ca`.
5. **`publish(entry, locale)`** — the only function that changes status: set `published`, snapshot a version, revalidate that tag. Scheduled publishing is one cron route that calls the same function.

#### Rules that keep it small and stable
- **Deps (short list):** `next`, `drizzle-orm` + `postgres`, `zod`, `@node-rs/argon2`, `sharp`, AWS S3 SDK, `nodemailer`. Nothing else without a written reason.
- **Auth:** email + password, argon2id, session cookie backed by `sessions`, CSRF, login rate-limit; ~150 lines in one file. Permissions: one `can(user, action)` function. No SSO, no user-defined roles. **Users screen (admin only):** create user, change role, reset password, delete. Passwords min 12 chars; role change / password reset / own password change sign the user out everywhere; the last admin can't be demoted or deleted, and nobody can demote or delete themselves. Every user has "El meu compte" to change their own password.
- **Draft vs live:** editable columns on `entry_translations` are the draft; `live` (jsonb) is the validated snapshot the public site serves. Saving never changes what is live; only `publish()` copies draft → live. Status: `scheduled` if a future publish is pending, else `published` if `live` exists, else `draft`.
- **Versions:** on publish, copy the translation row into `entry_versions` (keep last 10). Restore = copy back. No diff UI.
- **Media:** uploaded through the app (`POST /api/media`, logged-in users only), not presigned browser uploads, so every file is checked on the server: real type detected from bytes, images re-encoded by `sharp` to WebP at 3 fixed widths (480/960/1600, never upscaled, metadata stripped), documents (PDF, Word .docx, Excel .xlsx, PowerPoint .pptx) stored as-is, SVG rejected, max 15 MB. **Alt text per language is required** on any image before its page can be published. A file in use (by id, or by its shareable link in a page or the settings) can't be deleted.
- **Media library (client request 2026-10-02, "like WordPress"):** *Fitxers i imatges* in the admin: drag-and-drop upload with progress, search by name, filter images/documents, and a **public shareable link** per file, `/fitxers/<code>/<name>` on the website (`app/fitxers/[code]/[name]/route.ts`: code = first 8 hex digits of the id, kept unique on upload; the name is decorative). It redirects to the file in the public media bucket (images: the 1600px WebP), cached with the site so links survive a database outage; deleting a file expires it. Everything in the library is public to anyone with the link: never for internal or personal documents (those belong in the CRM's private files).
- **Public reads** go through one `getEntry(type, slug, locale)` returning only `published`; pages are ISR with tag revalidation.
- **Migrations:** plain SQL files in git, applied by one script; run automatically in staging, by hand (reviewed) in production.
- **Tests:** unit tests for section validation, `can()`, `publish()`, the public queries, media pipeline and the lead pipeline (throwaway DB); Playwright end-to-end suite (login throttle, draft → publish → live, hidden draft edits, unpublish, scheduled publish via cron, editor permissions) run in CI on every change.
- **Size budget:** whole CMS (admin + API + registry) soft target of ~6,000 lines. It is a guideline, not a hard stop (decision: flexible). When it is exceeded, say so and review for simplification before adding more; current size is recorded in the phase notes.

#### How to extend
| Need | Change |
|---|---|
| New section type | add its entry in `packages/sections/src/registry.ts` and its renderer in `apps/web/sections/render.tsx` |
| New field type in form builder | add one entry to `packages/forms/fieldTypes.ts` (validate + render) |
| New language | add locale code to config + one row of UI strings |
| New content type later (CRM, projects) | new table + config for the generic screens |

#### Non-goals
Plugin system, GraphQL, real-time collaboration, comments, freeform (pixel) positioning, custom-fields UI, theme editor, rich-text canvas (text sections allow only paragraph, bold, italic, link, list).

Full detail and phase plan: `PLAN.md`.

## Content model

Seven content types, each translatable into Catalan, Spanish and English (`/ca/`, `/es/`, `/en/` URL prefixes, alternate-language tags):

| Type | Purpose | Key fields |
|---|---|---|
| Post | Blog articles | Title, slug, sections (see below), author, category, tags, cover image, publish date, status |
| Landing page | Themed page | Title, slug, theme, sections, form, SEO fields, status |
| Section | One block in a post/page's ordered list | Type (header, text, image, embed, form, CTA, tile row, card grid…), fields per type, order |
| Category / tag | Grouping and nav | Name, slug, translations |
| Form | Lead/response capture | Fields (see form builder below), destination, consent text, notifications |
| Media | Images/files | File, alt text per language, credit |
| Site settings | Global elements | Nav, footer, default SEO, contact details, cookie text |

Status is draft / scheduled / published, per language independently, so a page can go live in one language before others are translated.

### Editor UI (posts and landing pages, same mechanism)

- Each page/post is an ordered list of sections.
- Staff add a section from a fixed picker, fill its fields (heading, body text, image, link), reorder with up/down controls, remove with an ✕.
- No freeform positioning, resizing, or free style overrides — only the brand style choices of the visual builder (phase 13).
- Embeds are restricted to **YouTube and Adobe (Express/Acrobat/Creative Cloud)** only, via pasted link — no generic embed-code field.
- Author, category, date, per-language publish status and SEO fields live in a side panel (see mockup).

### Form builder (Fillout replacement)

Build Apex's own form builder — same list-based mechanism as the section editor, not a canvas:

- **Field types:** short text, long text, email, phone, number, dropdown, multiple choice, checkbox, date, file upload, section/page break (multi-step forms).
- **Conditional logic:** show/hide a field based on an earlier answer.
- **Validation:** required fields, email format, number ranges.
- **Sharing:** a link and an embeddable version.
- **Destination is configurable per form**, set when the form is built:
  - create/update a CRM contact + lead, or
  - attach submissions to a project/client record, or
  - collect responses only, no CRM link.
- **Notifications:** email to staff on submission; optional confirmation email to the respondent.
- **Reporting:** submission count and completion rate per form; export submissions as a spreadsheet.
- **Explicitly out of scope for v1:** payments, e-signatures (planned as a separate app, see "Signatures app" at the end of this file), free-form formulas (calculated results exist, see the Forms app section), custom per-form styling. Add only if a concrete need arises later.
- See the "FormBuilder" mockup artboard for the UI (field list + destination panel + notification toggles).

## Lead capture pipeline

Every form submission (from a landing page or a standalone form) goes through the same flow:

1. Browser submits to the Apex API — never directly to the database.
2. API validates, rejects spam (honeypot field, rate limit, privacy-friendly bot check), and stores the exact consent text + timestamp.
3. If the email exists, update that contact and add a new lead; otherwise create the contact.
4. Tag the lead with source page, theme, language, and any UTM campaign parameters.
5. Route to the form's configured destination (CRM lead / project record / responses only).
6. Notify staff; show the visitor a confirmation.

Newsletter opt-in is a separate, unticked checkbox — never bundled into a general contact-request consent.

## Build order

1. **Repository, environments, database** — one repo, both apps run locally with one command; local/staging/production each with their own DB and secrets; daily backups with a tested restore.
2. **Backend content tools (custom CMS)** — seven content types, three languages, roles (admin/editor), draft/scheduled/published states. Done when an editor can draft and publish a translated post using the section-list editor.
3. **Public site rendering** — language-prefixed routes, section renderer, blog index/post/category pages, sitemap, robots, error pages. Done when a published page appears live within a minute, no full redeploy.
4. **Design foundation** — implement the tokens above as the base component library (header, footer, buttons, cards, form fields), mobile-first, accessible. Done when every section looks right at phone and desktop widths.
5. **Forms and lead pipeline** — build the form builder and wire it to the pipeline above. Done when a test submission reaches the CRM with correct source tags and consent record.
6. **Consent and legal pages** — cookie banner (accept/reject, equal prominence), privacy policy, legal notice, consent records on forms. Done when no non-essential script loads before consent.
7. **Deployment pipeline** — checks + build on every change, auto-deploy to staging, deploy to production on approval, domain + HTTPS. Done when a commit reaches staging with no manual steps.
8. **Monitoring and handover** — error tracking, uptime check, backup alerts, a short editor guide.

Rough estimate: 6–8 weeks for one full-time developer, before the form builder was added (~1–2 extra weeks); refine once the stack is confirmed.

## Public site (phase 3)
- **URLs:** `/{ca|es|en}/…` — home `/{l}`, landing pages `/{l}/{slug}`, blog `/{l}/blog`, post `/{l}/blog/{slug}`, category `/{l}/blog/categoria/{slug}`. Paths without a language go to `/ca` (`proxy.ts`). Reserved slugs (`blog`, `categoria`, `admin`, `api`, `sitemap`, `robots`) can't be published.
- **Homepage** is a landing page chosen in *Configuració*; nav, footer, contact, legal links and default SEO also live there (same field language as sections). A language without a live homepage redirects to `/ca`.
- **Caching = the outage rule.** Pages are generated on first visit and cached (ISR). All public reads use one cache tag, `content`; publish, unpublish, delete, scheduled publish, settings, categories and media edits expire it. Result: an edit is live in well under a second, and cached pages keep being served if the database is down. A page nobody has opened since the last change is not cached yet, so `scripts/warm.sh` (fetches every sitemap URL) runs after each deploy and every few minutes from cron. A build never needs the database.
- **Lists** show the latest 60 posts (no pagination yet, deliberate). **Embeds** load only after a click (no third-party request before consent). **Forms** sections render nothing until phase 5. `latestPosts` is an automatic news grid section.
- **SEO:** per-page title/description, canonical, hreflang (+ x-default), Open Graph/Twitter, `sitemap.xml` with alternates, `robots.txt`, localized 404/error pages.

## Design foundation (phase 4)
- **One tokens file:** `packages/ui/src/tokens.css` holds every colour, type size, space, radius and shadow; the public site and the admin both read it. Nothing else defines a colour. To rebrand, edit that file.
- **Contrast rules (enforced by `lib/__tests__/contrast.test.ts`, which parses the tokens file):** `--field-border` `#857E76` is only for input outlines (needs 3:1); small grey text uses `--text2` `#4D4741` (7.6:1+); white on the red header passes (5.4:1); accent `#D50032` is fine on light backgrounds but **must not be used for small text on dark panels** (3.4:1) — use ivory there (the hero label uses ivory with a red bar).
- **Component library:** `components/ui/` — `Button`, `Card`, and accessible form fields (`TextField`, `TextAreaField`, `SelectField`, `CheckboxField`, `RadioGroup`: visible label, hint/error wired with `aria-describedby`, `aria-invalid`, 44px touch targets). Site pieces (`Shell`, header, footer, `PostCard`, section renderers) live in `components/site/` and `sections/render.tsx`.
- **Styleguide:** `/styleguide` (local/e2e only, 404 in production) shows tokens with live contrast ratios, type, buttons, form fields in every state, cards and all section types.
- **Accessibility checks on every change:** `e2e/design.spec.ts` runs axe (WCAG 2.2 AA) plus sideways-overflow and 44px touch-target checks on every public page at 320 / 375 / 768 / 1024 / 1440 px, and keyboard tests (skip link, mobile menu, visible focus).
- **Mockup fidelity:** at 1440px the header, hero (460px, 48px headline, label + two buttons), tiles, cards (170px image), 3- and 4-column grids and footer columns match the approved homepage mockup. The newsletter band needs the form pipeline and lands with phase 5/6.

## Forms and lead pipeline (phase 5)
- **Builder:** *Formularis* in the Forms app (`apps/forms`, see the last section). A form is an ordered list of typed fields (same mechanism as page sections; ↑ ↓ ✕). Field types live in one registry, `lib/forms/fieldTypes.ts` (short/long text, email, phone, number, dropdown, multiple choice (one/many), checkbox, date, file upload, page break); adding a type = one registry entry + its check in `lib/forms/validate.ts` + its input in `components/site/form/Inputs.tsx`. Every label, help text, option and message is per language (CA/ES/EN, Catalan fallback). Conditional logic (`showField/showOp/showValue`) may only depend on an *earlier* field and is checked on save. Number ranges, required, email/phone/date formats are validated in the browser **and** again on the server (the server is the only one that counts).
- **Pipeline (`lib/forms/submit.ts`, one transaction):** browser → `POST /api/forms/{slug}/submit` (never the database) → honeypot → bot check → rate limit → validation of *visible* fields only → consent → files → in one transaction: submission (answers stored as a snapshot of label+value, so later form edits never rewrite history), contact upsert by email (blank values never erase known data), lead tagged with source page, page theme, language and UTM, newsletter opt-in, email outbox. Destination per form: *contact + lead* or *responses only*; *attach to project/client* attaches to a record of the minimal Projects module (phase 6).
- **Consent & newsletter:** the exact consent wording and a timestamp are stored on every submission. The newsletter box is a separate, unticked checkbox with its own stored wording (`newsletter_optins`); consenting to the privacy policy never subscribes anyone. Pushing opt-ins to the external newsletter tool is a later step (the table has `synced_at` for it).
- **Spam defences (no third parties, no cookies):** hidden honeypot field; a signed, expiring, single-use proof-of-work challenge solved by the visitor's browser (`lib/forms/pow.ts`; needs `BOT_SECRET`); rate limit of 5 submissions per address per form per 10 min and 20 per hour, using a keyed hash of the address that is purged after 24 h. **The reverse proxy in front of the app must append the client address to `X-Forwarded-For` (see `TRUSTED_PROXY_HOPS`).**
- **Files:** identified by content (PDF, images, Word, Excel), 10 MB max, stored in a **private** bucket (`S3_PRIVATE_BUCKET`), downloaded by staff through 60-second signed links after a login check. No antivirus scanning yet (note for hosting).
- **Email:** plain text via SMTP (`SMTP_URL`, `MAIL_FROM`). Emails are written to an `outbox` table in the same transaction as the submission and sent afterwards with retries (1 min → 24 h, 8 attempts, then flagged "dead" in the admin), so a mail outage never loses a notification or blocks the visitor. `POST /api/cron/tick` (every minute) publishes due scheduled content, sends/retries emails and purges old address hashes.
- **Reporting:** per form: submissions, anonymous "started" counter (no cookie, no personal data) and completion rate; CSV export (UTF-8 BOM, `;` separated, spreadsheet formulas neutralised); responses screen with paging; *Contactes* list (phase 9 makes it a lead manager). **Erasure:** admins can erase a contact with all their leads, submissions, files and newsletter opt-in; any editor can delete a single response; deleting a form deletes its responses and files.
- **Sharing:** link `/{locale}/form/{slug}` (not indexed), embeddable `/embed/{locale}/form/{slug}` (iframe code shown in the builder; the only place other sites may frame), or the *Formulari* section inside any page/post. Forms are cached with the site; staff notification addresses are never sent to the browser.
- **Security headers:** `nosniff`, referrer policy, permissions policy on every route; admin and API cannot be framed; public pages only by themselves. The Content-Security-Policy is set per request (see phase 6).
- **Known limits (deliberate):** UTM tags come from the address the visitor is on when submitting, plus the remembered campaign if they allowed *Campaign source*; forms need JavaScript (the bot check does); XLSX is not offered, CSV opens in Excel/Sheets; uploaded files are not virus-scanned (do it at the hosting layer).

## Projects module, consent and hardening (phase 6)
- **Projects module (deliberately minimal):** *Clients* and *Projects* (name, client, status active/paused/done, notes) in the admin. A form with destination *Adjuntar a un projecte o client* attaches every response to ONE chosen project or client (no contact/lead is created); the record page lists the attached responses. Deleting a project/client never deletes responses (they simply become unattached). The full CRM / ERP / project-manager screens (tasks, invoicing, documents, client portal) remain later phases.
- **Cookie consent:** one first-party cookie `apex_consent` (necessary: it only stores the choice; 6 months, versioned, then we ask again). Categories: *Necessary* (always on), *Campaign source* (remember `utm_*` in `sessionStorage` while browsing so it reaches the lead) and *External content* (YouTube/Adobe embeds load automatically instead of after a click). Accept and reject look identical; "Configure" opens a keyboard-operable dialog; a "Cookie settings" link is in every footer and any link to `#cookie-settings` (also inside page text) reopens it. Withdrawing consent erases what was kept. Nothing non-essential runs before a yes. Everything the site stores is declared once in `lib/consent/registry.ts`; the *Llista de cookies* section renders the public cookie declaration from it, so the text cannot drift from reality. **Add a new cookie/tracker = add it to that registry first.**
- **Legal pages:** privacy policy and legal notice are ordinary pages in the CMS, but their wording (entity, tax id, address, purposes, retention, rights) **must come from the client's legal adviser** — the demo seed only creates clearly marked placeholders. Add them to *Configuració → Enllaços legals*.
- **Content-Security-Policy** (`lib/csp.ts`, applied per request in `proxy.ts`): no third-party script can run (enforced by the browser, tested), frames only from YouTube/Adobe, images/media only from our own origin and the media bucket, `object-src 'none'`, `form-action 'self'`; admin and API can never be framed, public pages only by themselves, `/embed` by anyone. Trade-off: `'unsafe-inline'` for scripts/styles (cached pages cannot carry per-request nonces).
- **Client address behind a proxy:** `TRUSTED_PROXY_HOPS` (default 1) counts `X-Forwarded-For` entries from the RIGHT, so a visitor cannot spoof their address to dodge the rate limit; works with any proxy that appends the address (Caddy, nginx, most load balancers). Reference proxy config: `deploy/Caddyfile`; its staff-only rule is exercised by `scripts/caddy-drill.sh` (TLS certificates and real client addresses still need checking on the real server).

- **Menu:** *Configuració → Menú principal*: up to 8 entries, each either a link or a section with a **submenu** (up to 12 links). Desktop (≥1100px): accessible dropdowns (real buttons with `aria-expanded`; Enter/Space opens, Tab walks the links, Escape closes and returns focus, click outside closes; hover also opens). Below 1100px: the "Menú" panel with expandable sections. An entry needs a link or a submenu (checked on save).
- **Header buttons:** *Configuració → Botons de dalt* (up to 3, label per language, link may be an external site, white or outline on the red header) — this is where **"Campus virtual"** goes.
- **Social links:** *Xarxes socials* (Facebook, X, Instagram, YouTube, LinkedIn) as labelled icons in the top bar. Plus the phone/email, language switcher and footer already described.
- **Demo data:** `seed:demo` loads the real section structure (El GREMI, Laboral, Formació, Actualitat, Borsa de treball, Agremia't) with placeholder pages marked `[CONTINGUT PENDENT DE MIGRAR]`; the Campus link is a placeholder (`https://campus.example`) until the real address is set. Migrating the actual page content from gremi.net is a separate task.
- **Site search:** a plain GET form in the header (and mobile menu) → `/{locale}/search?q=` (`lib/search.ts`): Postgres over the LIVE snapshot only, accent/case-insensitive (also the Catalan middle dot), every word must match, title matches first, 20 results, `noindex`. No extension, no index, no service. It is the one public page rendered per request (needs the database); `search` is a reserved slug.

## CI and deployment foundation (phase 7)
- **CI** (`.github/workflows/ci.yml`, three parallel jobs; the logic is in `scripts/ci.sh` so it runs identically on a laptop: `pnpm verify`, or `pnpm verify:fast`): (1) lockfile-exact install, lint, types, unit + database tests, a **build with no configuration and no database**, the full Playwright end-to-end suite (accessibility, consent, forms, security headers); (2) the production **Docker image** is built and smoke-tested on a fresh database (`scripts/docker-smoke.sh`: migrations, pages, headers, startup refusal, native libraries, first admin); (3) `pnpm audit` for known vulnerabilities. Dependabot opens weekly update PRs (npm, GitHub Actions, Docker); CI decides if they are safe. The workflow file itself has not been run on GitHub yet (only its script and its YAML validity were verified here).

## Client portal (phase 11, deliberately small)
- **Isolation by construction:** portal accounts are a SEPARATE system from staff users: own tables (`portal_users`, `portal_sessions`, `portal_tokens`), own cookie (`apex_portal`, path `/portal`), own pages under `/portal` (outside the `/{locale}` site and outside `/admin`). ## Forms app (third app, plan `docs/forms-app-plan.md`; F1, F2 and F3 done)
- **What:** `apps/forms` (Sam, port 3002, host `forms.<domain>` staff-only like the CRM) owns the form builder (*Formularis*), the responses (list, CSV export, signed downloads of uploaded files, delete a response), the public submission API `/api/forms/{slug}/{challenge,start,submit}` (the whole lead pipeline in `packages/forms`), and will host the Fillout-like features of `docs/forms-v2-plan.md`. Own login (cookie `apex_forms_session`, same `users`), "El meu compte", `/api/health`, `/api/cron/tick` (sends the outbox, purges address hashes, trims the error log), robots, CSP, never framable. After a form is saved or deleted it asks the website to refresh its cache (`lib/web-cache.ts`, `WEB_INTERNAL_URL` + `CRON_SECRET`).
- **What did not move (decision during F2):** the standalone page `/{locale}/form/{slug}`, the embed `/embed/{locale}/form/{slug}` and forms inside pages are still drawn by `apps/web` (they use the site shell and consent banner and only READ `forms`), so public URLs do not change. The browser posts to `/api/forms/*` on the public address, which reaches the Forms app (Caddy in production, the website's `proxy.ts` with `FORMS_INTERNAL_URL` in development and tests).
- **Response views (Forms v2, item 10, no migration):** the responses page of a form has three views, **Targetes** (the original list, paged in the database), **Taula** (one column per question, answers cut to 80 characters, files still download through the signed link) and **Tauler** (a lane per option of a choice question, then "Sense resposta"; choose the question with *Agrupa per*; a multiple choice sits in every lane it picked; read-only: a card opens the whole response), plus search (every word, accents and case ignored, over every answer) and a filter *question = value*. They are built **inside the Forms app, not in the CRM workspace** (apps never import each other, and the workspace engine is for CRM tables with code-defined entities, not per-form columns); the pure logic is `packages/forms/src/response-views.ts`. Table, board, search and filter look at the latest 2000 responses (the plain card list pages in the database); responses cannot be edited or moved from here (changing a response stays a decision of the respondent through their private link, item 4c).
- **Analytics (Forms v2, item 9, migration 0026):** *Estadístiques* page of a form (`/admin/forms/{id}/analytics`, pure maths in `packages/forms/src/analytics.ts`): responses, starts, completion rate, time to complete (median and average), responses per day (last 30, Catalonia's calendar), drop-off per question and a bar chart per choice question (drop-downs, multiple choice, yes/no, boxes, ratings with their average). Over the latest 5000 responses. **Anonymous by design, no cookie and nothing about the person:** *time* = seconds from the signed challenge's issue (the first touch of the form) to sending, stored as `submissions.duration_seconds` (the expiry is signed, so it cannot be forged); *drop-off* = `form_field_reach`, ONE total per question (no day, no address, no session) incremented by `POST /api/forms/{slug}/reach` the first time a page load focuses that question (only a real question of an open form counts; anyone can inflate the totals, which is acceptable for statistics and is why they are never used for decisions in the pipeline). Responses before this feature have no time and no reach data (shown as unknown). Charts are bars with the figures written beside them, never colour alone.
- **Prefill from the link (Forms v2, item 8, no migration):** a question may have a *link name* (`prefill`, e.g. `empresa`), so `/ca/form/inscripcio?empresa=Gràfiques%20Vila&nivell=Premium` opens with those fields filled. **Whitelist by construction:** only fields that have a link name are ever filled; nothing else in the address is read (unknown names, `utm_*` tags and the private `resume` / `edit` links are untouched, and those names are reserved so a field cannot claim them). Kinds: text, long text, email, phone, number, drop-down, multiple choice (several with `a|b`), box (can only be pre-ticked), date, rating, yes/no, web address (not files, addresses or results). **A value must pass the very same check as a typed answer** (`validateAnswers` on that one field: an option that does not exist, a mark outside the scale, a malformed email are ignored, never shown), is cut at 500 characters and is only a starting point: the visitor sees and can change it, and the server validates the answer again as always. It runs in the browser only (`FormRenderer`), so the cached page stays the same for everyone and nothing is sent anywhere; it is skipped when a draft or a sent response is being opened. Checked on save: format (lowercase letters, digits, `-`, `_`, up to 30), not reserved, not used twice. **Privacy:** an address is kept in browser history and in the web server's access log, so links must never carry anything sensitive (no ID numbers, no health or finance data); a name and an email in a mailing link is the intended use.
- **Calculated fields (Forms v2, item 7, no migration):** type `calculated` (*Resultat calculat*) gives a total, score or average from earlier questions. **It is a choice from a short list, never a formula typed as text**: `op` (sum / average / min / max) over `terms` (earlier questions, each with an optional weight), a fixed `offset`, `decimals`; nothing is parsed or evaluated, so there is nothing to inject and nothing that can loop (`packages/forms/src/calculate.ts`). What each question is worth: a number or mark as it is, Sí = 1 / No = 0, a ticked box = 1, a drop-down / multiple choice = the **points** typed on its options (no points = 0; the builder refuses a calculation over options without any). A hidden or unanswered question does not count. **The server always computes the value itself** in `validateAnswers` from the validated answers (what a browser sends for it is ignored) and stores it with the response like any answer (type `calculated`, so staff screens, emails, the spreadsheet and webhooks show it); `show: yes` also shows the visitor the total live, worked out by the very same function in the browser. It has no answer of its own (`input: false`), so it is not in drafts, cannot be mapped to CRM records and cannot control other fields. Checked on save: at least one question, none twice, only earlier ones, only countable kinds, numeric weights, offset and points.
- **Records as a destination (Forms v2, item 6, migration 0025):** a form can have destination `records` (editor: *Crear registres al CRM*): each response creates or completes **a person**, **an event registration** (person + attendance, once per person and event), **a labour case**, **a training request** or **a job-board candidate**. **Architecture = the queue option (B) of `docs/forms-app-plan.md`, on purpose:** the Forms app never writes these CRM tables (that would have widened its exception from three rows to five tables and bypassed the CRM's validation and history). It stores the response with `submissions.routing_status = 'pending'` and the setup in `forms.routing` (`{target, map: {recordValue: formFieldId}, fixed: {…}}`); **the CRM app's scheduler (`apps/crm/lib/form-routing.ts`, run by `/api/cron/tick`) creates the records THROUGH THE RECORDS ENGINE** (`saveRecord`: the same validation, the same change history, naming the form as the author with no user id) and reports back in the routing columns, the only columns of `submissions` the CRM may update (`db/grants.sql`, column-level `UPDATE`); the Forms app may read `events` to offer them in the editor. **The contract between the two apps is `packages/forms/src/routing.ts`** (what each target is, which values a form field can fill, which settings staff choose); `checkRouting` runs when the form is saved and again before the CRM acts, and a CRM test fails if a target names an entity or field that does not exist. **Rules:** an existing person (found by email, archived ones ignored) is **only completed, never overwritten** (the CRM is the source of truth); a company is linked only when exactly one company has that name; a record is created once per response (`external_ref = form:<response id>`, so a retry after a crash never duplicates it); a repeat registration changes nothing except an *invited* person becoming *confirmed*; a registration form cannot mark anyone as having attended; a job candidate gets the consent date of the response, the registration date and a retention date from a choice staff must make (no default; applying again only moves dates forward). **Failures:** a problem with the setup or the data (event deleted, value refused by the record, mapping broken) fails the response **at once** with a readable reason; an unexpected error is retried on the next runs, 3 attempts. Staff see *Pendent / Passat al CRM (what was created) / No s'ha pogut passar al CRM* on every response, a warning on the forms list, and *Torna-ho a provar*. Latency is the scheduler's (about a minute). Edits of a sent response afterwards do not change records already created. Capacity of an event is not enforced (known gap).
- **Webhooks (Forms v2, item 5, migration 0024):** a form (*Integracions* page, up to 5 endpoints) tells other systems when a response is sent (`response.created`) or changed by the respondent (`response.updated`, with `changes` and `editCount`); `ping` is the staff test button. **Delivery is the outbox pattern:** a `webhook_deliveries` row is written **in the same transaction** as the response (a crash never loses one; a refused response queues nothing), then sent right after the request (`after()`) and by the Forms scheduler with `SKIP LOCKED` claims, backoff 1, 5, 15, 60, 180, 360, 720 minutes, **dead after 8 attempts** (shown on the page, *Torna-ho a provar* resets it); the delivery id is the same on every retry (`X-Apex-Delivery`, and `delivery` in the body) so receivers can ignore duplicates. **Signature:** header `X-Apex-Signature: t=<unix>,v1=<hex>` = HMAC-SHA256 of `<t>.<raw body>` with the endpoint's secret (`whsec_…`, shown to staff of the Forms app; *Canvia el secret* rotates it); the page documents the check and the 5-minute tolerance. **Payload:** form, response (id, date, locale, page, theme, UTM, every answer with label, type, value and a readable `text`); **files are named, never included and never with their storage key**. **SSRF is defended in depth (packages/forms/src/webhooks.ts):** https only, no credentials, public hosts only (no private, loopback, link-local, metadata, shared or reserved ranges, IPv4-in-IPv6 judged by the IPv4 inside, 6to4 and Teredo refused, internal-looking names refused), and **the address is checked again at connection time by a guarded DNS lookup** so a name that resolves to an internal address (rebinding) is refused; redirects are never followed (a 3xx is a failed attempt), 8 s total timeout, 256 KB payload cap, only the first bytes of an answer are read. `WEBHOOK_ALLOW_PRIVATE=1` lets webhooks call this machine for development and the e2e receiver; **a staging or production server refuses to start with it set** (`checkEnv`) and the code ignores it there. **Privacy:** a payload holds response data, so deliveries are deleted **with the response** (erasure cascades) and 30 days after they finish (scheduler); the page tells staff to mention the receiving systems in the privacy text. Deliveries and secrets belong to `apex_forms` only (boundary drill). No new environment variable, no new dependency (`node:http`, `node:net`).
- **Editing a sent response (Forms v2, item 4c, migration 0023):** opt-in per form (`forms.allow_edits`, default off). When on, the secret link `<page>?edit=<secret>` is made when the response is sent and shown **once** on the thank-you screen (instead of redirecting: it would be lost) and added to the respondent's confirmation email; **only its SHA-256 is stored** (`submissions.edit_token_hash`, unique). Rules in `packages/forms/src/edit.ts`: it works **30 days from sending**, while the form is switched on and **not past its end date** (a form that is merely full still lets people correct what they sent: the limit is about new responses) and staff can switch it off at any time; wrong, malformed, expired, other-form and switched-off all answer the same 404. **What can change:** the answers, validated again against the form **as it is now** (a required field added since must be filled; a field hidden by a condition now drops its answer; a field removed since keeps its old answer; **files are never changed or lost**). **The email mapped to the contact is locked** (disabled in the page and held at its original value on the server whatever the browser sends), so the link can never re-point the CRM contact; name, phone and company follow the response to the contact (a blank never erases). **The first version is kept** (`original_answers`, saved the first time) and staff see *Modificada n cops* and the original on the responses screen; consent given when sending is untouched. **Limits:** one save per second, 20 edits per response; changing nothing writes nothing and notifies nobody. Staff are mailed the exact changes (`label: old → new`) when staff mail is on. API: `POST /api/forms/{slug}/response/load` and `/response/update`. Privacy: the link is a bearer secret in the respondent's hands (the thank-you text tells them to keep it private); nothing is stored in the browser.
- **Save and resume (Forms v2, item 4b, migration 0022):** opt-in per form (`forms.allow_drafts`, default off, so no existing form changes). A visitor presses *Desa i continua més tard*, optionally gives an email, and gets a private link `<page>?resume=<secret>` (also mailed). **The secret is 256 random bits and only its SHA-256 is stored** (`form_drafts.token_hash`); it lives only in the link and in the page's memory (no cookie, no browser storage, so nothing to declare in the consent registry). A draft keeps **text answers only, never files**, cleaned against the form's own fields (unknown ids, files, nested junk and oversized values dropped; at most 64 KB) and cleaned again against the form as it is when it is opened; it **expires 30 days after the last save and is deleted when the form is sent** (the submit transaction deletes the draft of that form and secret; a refused submission keeps it). Opening it restores the answers and the step (or the nearest step that still applies). Unknown, tampered and expired secrets all answer the same. **Abuse limits:** creating a draft needs the bot check (single use, recorded in `challenge_id`), 10 drafts per address and form per hour, 3 mails per email address per day (counted with a keyed hash; **the address itself is never stored**), one save per second per draft; hashed addresses are cleared after 24 h by the scheduler (`purgeDrafts`, run from the Forms tick through `purgeIpHashes`). A person can delete their own draft (*Esborra l'esborrany*). API (all under `/api/forms/{slug}/draft`): `POST` create/update, `POST /load`, `POST /delete`; `form_drafts` belongs to `apex_forms` only (the website and the CRM cannot read it: boundary drill). **Privacy:** these are personal data before consent, which the editor card *Esborranys* tells staff to mention in the privacy text. Logic in `packages/forms/src/drafts.ts`, UI in `components/SaveForLater.tsx`.
- **Availability and ending (Forms v2, item 4a, migration 0021):** `forms.closes_at`, `forms.max_responses` and `forms.redirect_url` (all optional; a form without them behaves exactly as before). **`availability()` / `stateOf()` in `packages/forms/src/availability.ts` is the one answer to "is this form accepting responses?"** (switched off wins, then the end date, then the limit; states `open`, `closed`, `expired`, `full`): the pipeline, the challenge/start API, the editor chip and the list all use it. The end date is typed in Catalonia's time (`apps/forms/lib/madrid-time.ts`, correct across the clock changes) and stored as an exact instant. **The limit is enforced inside the submit transaction with a row lock on the form**, so many visitors at the same moment can never exceed it (tested with 8 concurrent submissions for 3 places); deleting a response frees its place. The public page is cached and cannot know that the end date passed or the last place was taken (and the website's database user may not read responses), so a form with an end date or a limit (`PublicForm.checkOpen`) asks `GET /api/forms/{slug}/status` (answers only `{open}`, never why or how many) when the page opens, never while someone is typing and never from the visitor's own clock; any failure leaves the form usable, and the challenge API answers 410 so a form that closes meanwhile tells the visitor instead of failing. The redirect is a path of this site or an http(s) address (`cleanRedirect`: no scripts, other schemes, credentials or `//host`), validated on save and again in the browser; the confirmation message stays as the fallback. Multi-step forms show a progress bar (`<progress>`) next to "Pas x de y".
- **Conditional logic (Forms v2, item 3):** a field, title/paragraph or **page break** can be shown only if conditions hold. The first condition keeps the keys every saved form already has (`showField`, `showOp`, `showValue`), so nothing was migrated; optional `showExtra` (a list of up to 5 more `{field, op, value}`) and `showMatch` (`all` default, or `any`) add to it (`conditionsOf` in `fieldTypes.ts` reads them all). Operators: `equals`, `not_equals`, `contains` (case- and accent-insensitive, text-like fields only), `empty`, `not_empty` (an unticked box and a blank text are empty; No to a yes/no is an answer). **One evaluator, `visibility(items, answers)` in `validate.ts`, serves the browser and the server**: each question is evaluated once (a long chain cannot blow up), a condition on a hidden field cannot hold, a condition on a deleted field is ignored, a loop in a hand-edited definition does not hang, and everything after a hidden page break is hidden (**skipped step**: not counted in "Pas x de y", its required fields are not enforced, its answers are dropped on the server). `shownSteps()` gives the renderer the steps to walk through, forward and back. Every condition is checked when the form is saved (`checkDefinition`: earlier answerable field, value valid for that field, a text to look for with *conté*), the message naming which of several conditions is wrong.
- **More field types (Forms v2, item 2):** besides the original eleven, `rating` (whole mark 1 to 5 or 1 to 10, stored as a number), `yesno` (stored as true/false; unanswered is `""`, different from No; a required one needs a choice), `url` (http(s) only, scheme optional and defaulted to https, no credentials, needs a real host: `cleanUrl` in `validate.ts`), `address` (stored as `{street, postalCode, city}`; a partly filled one needs street and city, a required one all three) and two display-only blocks, `heading` and `paragraph` (rendered with the site's safe rich-text; no answer is stored; they may be conditional but cannot control other fields). **Rules a new type must follow:** one registry entry (`fieldTypes.ts`), its case in `validateAnswers`, its input in `components/Inputs.tsx`, a case in `answer-text.ts` if its value is structured (**every screen, email and the CSV export format answers through `answerText`**, never by hand), and a test: the registry-guard test fails if a type that takes an answer accepts an empty required answer, so a type cannot ship without validation. Conditions on `yesno` use `yes`/`no`, on `rating` a mark inside the scale (checked when the form is saved).
- **Templates and copies (Forms v2, item 1):** *Formularis* offers starter templates (contact, event registration, course enrolment, job-seeker intake) in `apps/forms/lib/form-templates.ts`: plain data in the builder's own format, instantiated with fresh field ids, always created **closed**, with a neutral consent wording that the legal adviser's text must replace. A unit test runs every template through the builder's validation, checks it is fully translated and submits a valid response through the real pipeline, so a new template cannot ship broken. *Duplica* (list row and editor) copies the last saved definition and settings into a closed form with the next free slug (`-copia`, `-copia-2`...) and never copies responses (`lib/forms-copy.ts`). Adding a template = one entry in `formTemplates`.
- **CRM side:** the CRM keeps contacts, leads (status, owner, notes, conversion into a client), erasure and the lists that show responses (client, project and lead pages read `submissions` and `forms`); its menu links to the Forms app (`FORMS_URL`). Erasing a contact still removes its responses and files.
- **Rules:** `apps/forms` never imports `apps/web` or `apps/crm` and they never import it (`scripts/check-boundaries.sh`, with self-test). Database user `apex_forms` (`db/grants.sql`): owns `forms`, `form_starts`, `submissions`; reads `projects` and `clients` (destination pickers), `users` (and changes its own password), shared tables; and, decision A of the plan, may only upsert `contacts`, insert `leads` and upsert `newsletter_optins` (cannot read or change leads, delete anything of the CRM's). `scripts/boundary-drill.sh` proves it with the real roles, including that erasing a contact in the CRM cascades to its responses. The role must exist before `APPLY_GRANTS=1` (see `DEPLOY.md`).
- **Tests:** unit tests in `apps/forms/lib/__tests__` (own throwaway database `apex_test_forms`); `apps/forms/e2e/forms.spec.ts` (builder → visitor → lead, files, export, newsletter, embed, attach to a project: it signs in to the CRM too where it crosses) and `apps/crm/e2e/leads.spec.ts` (the CRM side of a response: follow-up, conversion, search, erasure).
- **Deploy (F3):** same image (`start-forms`), compose service `forms` (tag `APEX_TAG_FORMS`, optional `DATABASE_URL_FORMS`), Caddy host `FORMS_DOMAIN` (staff-only, own DNS record) and `/api/forms/*` on the main domain routed to it, `deploy.sh <tag> forms` with its own health check and rollback, a scheduler line and an uptime check of its own. Proven by `scripts/{docker-smoke,deploy-drill,staging-drill,caddy-drill}.sh`. First rollout on an existing server: `DEPLOY.md`, "First deployment of the Forms app" (DNS, the `apex_forms` role, `FORMS_URL`, `BOT_SECRET`, release with `all`).

## Signatures app (fifth app, PLANNED: `docs/esign-plan.md`; S0 and S1 done, S2 next; decided 2026-10-07, Sam)
- **What:** `apps/sign` (Sam, port 3004, host `SIGN_DOMAIN`, default `sign.<SITE_DOMAIN>`) will let staff send a PDF to one or more people to sign electronically. It is **built from scratch** (no hosted service, no AGPL platform such as Documenso/DocuSeal/OpenSign): same repository, same database, own staff cookie (`apex_sign_session`, same `users`), own `apex_sign` database role, own service and rollback. Pure logic goes in `packages/sign` (state machine, field geometry, audit text, PDF stamping and sealing); `apps/sign` and the other apps never import each other (`scripts/check-boundaries.sh` gets extended in S1).
- **Legal level:** **simple electronic signature (SES)** only: verified email link, explicit consent (exact wording stored with a timestamp), append-only audit trail, and a tamper-evident sealed PDF (PAdES seal + audit page). It never claims to be qualified or advanced. A document that legally needs a qualified signature goes to an external trust provider. **The consent wording, the retention period of sealed PDFs and audit trails and the list of allowed documents must come from the client's legal adviser** (placeholders until then).
- **Rules:** fixed typed fields placed by number/click (signature, initials, date, text), never a canvas; single-use signer links stored only as hashes; the server validates state, order and expiry; sealed PDFs and originals live in a **private** bucket and are downloaded by staff through a session check plus a 60-second signed link; the signer pages are `noindex`, not framable and use no third-party anything. The seal certificate comes from the environment and the app refuses to start in staging/production without it. New dependencies, each with a written reason: `pdf-lib` (MIT), `pdfjs-dist` (Apache-2.0), `@signpdf/signpdf` (MIT). Every new table also goes in `db/grants.sql` in the same PR.
- **Open decisions** are listed in section 9 of the plan (seal certificate: self-signed first; who signs; ordering; reminders and expiry; retention). S1 (the empty shell: login with its own cookie, health, tick, robots, CSP, role `apex_sign` with the shared tables only, e2e smoke test, boundary check and permission drill) is in place; nothing else is built yet.
